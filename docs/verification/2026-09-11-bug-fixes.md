# Bug fixes

Date: 2026-09-11
Verdict: **SHIP.** 240 tests pass across three consecutive runs, `tsc` clean, `next build` clean
from an empty `.next`, and `npm run lint` reports zero errors and zero warnings for the first time.

## The linter had never run

`npm run lint` crashed inside `@eslint/eslintrc`'s config validator with "Converting circular
structure to JSON", before reading a single file. Two earlier sessions noted it as broken and worked
around it.

The cause: `eslint.config.mjs` wrapped Next's configs in `FlatCompat`, which is the shim for
consuming OLD eslintrc-style configs from a flat config file. `eslint-config-next` 16 already
exports flat config arrays, so the shim was translating something that needed no translation and
crashed doing it. Loading them directly fixes it.

That matters because a linter that does not run finds nothing. On its first real run it found 29
problems, and four of them were genuine bugs the type checker cannot see.

## The four real bugs it found

**Reading a ref during render, in the CGM import screen.** `Paste.tsx` computed whether the Import
button was enabled from `raw.current`, a ref holding the file contents. React does not re-render
when a ref changes, so this worked only because a sibling `setState` in the same handler happened to
force a render. It would have broken silently the moment those updates moved or batched differently,
leaving the button disabled with a file loaded. Now derived from `lineCount`, which is state, is set
on both the file and the textarea paths, and is exactly the question being asked.

**Two components calling setState inside an effect.** `HeroVideo` read
`prefers-reduced-motion` in an effect and set state, so it rendered twice on every mount and the
first paint always assumed no motion. It is now `useSyncExternalStore`, which is the hook for a
value that lives outside React, with a server snapshot that returns the cautious answer. And
`PhotoEstimate` copied the action result into editable state in an effect, so the screen showed the
previous estimate for a frame before swapping; it now adjusts during render against the result
already absorbed, which is React's documented pattern for this.

**Six unescaped apostrophes** in JSX text, in two screens.

## Bugs fixed that the linter did not find

**The migration could only run once.** Adding `foods.source_date` generated an `ALTER TABLE ADD`
into the statement list. SQLite has no `add column if not exists`, so the first run succeeded and
every run after it failed with "duplicate column name". `bootstrapDeploy` calls that migration on
every single boot and logs a failure without stopping, so the live app would have booted with a
permanently broken migration step and no column added after that one would ever have landed. An
`ADD COLUMN` is now checked against `PRAGMA table_info` first, which is precise rather than
catching the error, because catching it would also swallow a genuinely malformed statement.

**The migration leaked a connection per account.** `applyAccountSchema` opens its own client and
never closed it. Invisible at signup, and a migration across a thousand accounts opening a thousand
connections and releasing none. On Windows it also blocks deleting the file, which was showing up as
an occasional test failure with no assertion attached. Four consecutive full-suite runs are clean
since.

**Signup had no rate limit at all.** Sign-in was limited throughout, eight per email and twenty-four
per address per fifteen minutes. Signup was not, on a public URL. That matters because the AI spend
caps are per ACCOUNT: they work exactly as designed and are the wrong shape for this, since total
spend is unbounded in the number of accounts. A script creating accounts spends the free tier once
per account, and nothing stopped it. Six per address per day now, counted from the table that
already exists, and it fails open on a read error because wrongly refusing somebody their first
account is worse than one extra getting through.

**An orphaned route that contradicted the app.** `src/app/gate/page.tsx` was the pre-authentication
shared-passphrase screen. Nothing linked to it, nothing read the cookie it set, it sat behind the
session gate so it was a passphrase form that required already being signed in, the environment
variable it depended on is no longer set, and its copy told visitors "there are no accounts in this
demonstration", which is false. Deleted, and recoverable from the commit.

**`drizzle.config.ts` pointed at the pre-migration backup.** Its default was `data/steady.db`, which
since the database split is the backup of the first account's data, so `npm run db:push` wrote
schema changes into a file the app never reads and could alter a backup. It points at a scratch file
now. drizzle-kit reads one config file and cannot be per-account, which is exactly why
`accountSchema.ts` and `npm run migrate:all` exist.

**Nineteen dead imports**, including six unused table imports in one file, plus one
ternary-as-statement rewritten as the branch it actually is. Two were deliberate unused parameters,
so the linter now respects the leading-underscore convention instead of the code being contorted.

## What I checked before changing anything

Two warnings looked like they might be hiding something worse and were not.

`checkSpendLimit` unused in `src/lib/data/coach.ts` could have meant the coach feature was
unmetered. It is metered, in `src/lib/ai/coach.ts`, immediately before the model call. The import
was just dead.

The unused expression in `src/lib/actions.ts` could have been a statement that was meant to do
something. It was a working ternary used for its side effect, collecting repeated form fields into
an array. Ugly, not wrong.

a gauge renders with no server errors in a freshly started dev server.

One note on a false alarm during this work. The browser console showed `GoalEdge is not defined`
across several navigations. It was a cached entry from a moment between two of my own edits, when
the dev server hot-reloaded a state where the component was used but not yet defined. A restarted
server serving the same page reports no errors, the function is defined and used, and the clean
build succeeded. Worth writing down because a stale console entry reads exactly like a live bug.
