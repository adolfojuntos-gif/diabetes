## The one that mattered

**The webhook was being redirected to the sign-in page, and Stripe cannot sign in.**

`/api/stripe/webhook` was not in the gate's public allowlist. Every delivery got a 307 to `/signin`.
Stripe reads a 307 as a delivered response, so it would not have retried and would not have alerted:
the events were simply dropped. Subscribers would have paid, their plan would never have moved, and
nothing in the app's own logs would have said why.

Every test passed throughout, in both directions, because they call the route handler directly and
never pass through the gate. One real HTTP request to the running server found it in a second.

There is now a test that reads the routes on disk and the allowlist in the gate and asserts they
agree: a route with no `requireAccount` authenticates its own callers, so it must be public. Negative
control run against the allowlist as it stood before the fix: it reports exactly
`/api/stripe/webhook`, and reports nothing after.

## Negative controls

Every assertion written this session was run against code that should fail it.

**The signature.** The pair is the control and needs no contrivance: the same payload, unsigned,
leaves the account on free; signed, it moves to plus. If verification were skipped the first case
would upgrade.

**The gate.** Described above.

**The caps against revenue.** Asserted as "worst case under caps is less than 60% of what a
subscription keeps", not against a fixed figure, so a future cap rise fails the test instead of
quietly inverting the margin. Worst case on Opus rates is $10.56 against $19.12 kept. The old caps
would have produced $299 and failed it.

**The plan writer.** A structural test allows exactly one file to write `accounts.plan`. Adding a
second writer anywhere fails it.

## Other things found by running rather than reading

**The refusal message chose its wording from the real clock.** `messageFor` compared the reset time
against `Date.now()` rather than the `now` it was given, so a verdict for a moment other than the
present described itself wrongly. It rendered "It frees up again on September 15" for a window that
frees in an hour. Found because a test used a fixed clock, which is the only reason it was visible.
It also said "frees up again on 3:20 pm", so the preposition was fixed with it.

**A zero allowance built an invalid date.** With a monthly maximum of zero there are no calls to read
a reset time from, so the general path produced `Invalid Date`. It is now an explicit branch with no
reset time and a different sentence, because waiting does not help and the honest answer names the
plan.

**The hint described a button that was not there.** With no Stripe keys the upgrade button is
correctly hidden, and the paragraph explaining what "the button" does rendered anyway. Found by
reading the rendered page, not the source.

**Nothing migrated the control plane.** Only the one-time account migration ever created those
tables, so adding two for billing had no path onto a running deployment: the table would not exist
and the first request to touch it would fail. `npm run migrate:all` now does the control plane first.

**A hard-coded row limit was a fail-open.** The limiter's audit query took 500 rows. Ample at the old
caps, and the moment a plan allows more, a truncated count makes somebody look under their limit when
they are over it. Derived from the largest cap now.

**Four tests restated the caps they were testing.** They had "10" and "40" written into both the
assertions and the reasoning in their comments, so tightening a cap failed them for no reason other
than the arithmetic living in two places. Rewritten to read every figure from the table.

## Not verified

- **No real Stripe call has ever been made.** No account, no keys, no price. The checkout session,
  the billing portal and the customer creation are written against the SDK and have never run. This
  is the largest gap and it is the first thing to close: criterion 9 is only half met.
- **The free plan's runtime degradation.** There is no Anthropic key on this machine, so every
  feature already takes its free path and a gated call cannot be told from an ungated one. Covered
  by unit tests and by the structural assertion that every model call site is metered, which is not
  the same as watching it happen.
- **Proration, coupons, annual billing, tax correctness.** Out of scope by decision. The economics
  doc notes annual billing is worth more to the margin than any model choice, so it is the obvious
  next piece.
- **A second paid tier.** `planForPrice` returns plus for any price, which is right with one tier and
  becomes a real lookup with two. The comment says so.
- **Clinician review of the 43 knowledge items.** Unchanged and still open. Not a billing task, and
  it still blocks selling to patients.

## Setting it up

These need a Stripe account. Run them yourself: the keys should not pass through anybody else.

```bash
# 1. In the Stripe dashboard, create a product with a recurring $20/month price.
# 2. Put the keys in .env.local (see .env.example for what each one is).
# 3. Forward webhooks to the local server and take the whsec_... it prints:
stripe listen --forward-to localhost:3140/api/stripe/webhook
```

```bash
# 4. On the deployment, set the same three as secrets, plus the public address:
flyctl secrets set STRIPE_SECRET_KEY=... STRIPE_WEBHOOK_SECRET=... STRIPE_PRICE_ID=... APP_URL=https://your-app.fly.dev
```

```bash
# 5. After any schema change, on every environment:
npm run migrate:all
```

The webhook endpoint to register in Stripe is `/api/stripe/webhook`, and the events worth sending are
`checkout.session.completed` plus the `customer.subscription.*` family.
